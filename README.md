# Shorthack

ИИ-помощник поддержки МИСИС: разбирает обращение, находит ответ в базе знаний,
а если ответа нет — собирает обращение и отправляет его в поддержку.

Языковая модель — **Groq** (OpenAI-совместимый API). Развёртывание — свой контейнер на нашем VPS.

## Быстрый старт

```bash
cp .env.example .env   # вписать GROQ_API_KEY
```

Секреты в репозиторий не коммитим: `.env` в `.gitignore`, в PR попадает только `.env.example`.
Ключ не пересылаем в чатах — только файлом на машине.

**Рабочий сервер: https://thinkers.itatmisis.ru** — там же `/docs` (Swagger) и `/api/health`.
Домен выдали организаторы на время хакатона; прямой адрес `http://45.87.41.186:8080` тоже жив
и нужен, если домен отберут раньше защиты.
Фронт можно разрабатывать прямо против него, CORS открыт: ждать чужой готовности не нужно.

**Локально:**
```bash
./run.sh          # venv, зависимости, uvicorn --reload на http://localhost:8000
./run.sh test     # прогон тестов
```

**В контейнере:**
```bash
docker compose up -d --build   # http://localhost:8000/docs
```
Данные (faq, schedule, app.db, cache, outbox) живут в томе `shorthack_data` и переживают пересборку образа.

**Деплой на сервер:** `./deploy.sh` — идемпотентно, поднимает только проект `shorthack`
и не трогает чужие контейнеры на VPS. `.env` на сервере заведён вручную и автодеплоем не перезаписывается.

**Перед защитой:** `python scripts/warm_cache.py --base-url https://thinkers.itatmisis.ru` —
прогрев кэша, иначе демо пойдёт в сеть и может словить лимит Groq (см. [scripts/README.md](scripts/README.md)).

## Идея

**ИИ-помощник поддержки МИСИС** — отдельный сайт, куда обучающийся или поступающий пишет
вопрос своими словами: про поступление, обучение или внеучебную деятельность. Помощник разбирает обращение и
делает одно из двух:

1. **Отвечает сам** — находит подходящий раздел на `misis.ru`, даёт короткую выжимку по сути
   вопроса и ссылку на первоисточник. Вопрос закрыт за секунды, заявка не создаётся.
2. **Предлагает создать заявку** — если ответа в базе нет, вопрос нетиповой или требует
   разбора человеком. Помощник заранее собирает всё, что нужно оператору, и дописывает
   недостающее уточняющими вопросами.

Роль — **поступающий, студент или преподаватель** — человек выбирает сам ползунком на
главном экране. Она задаёт, в какой части базы знаний искать и куда уйдёт обращение, поэтому
модели не приходится её угадывать.

Обращение можно отправить двумя способами. **С подтверждением почты** — человек вводит любой
адрес (у поступающих корпоративного нет), получает код, подтверждает владение ящиком и
получает ответ письмом. **Инкогнито** — без подтверждения: обращение дойдёт до поддержки и
попадёт в статистику, но ответить на него будет некуда, и об этом честно предупреждаем до
отправки.

Поступающие — половина аудитории и самая уязвимая её часть: у них ещё нет ни корпоративной
почты, ни личного кабинета, а вопросы самые срочные. Требовать от них корпоративный адрес
было бы отсечением половины пользователей.

### Зачем это нужно

Сейчас человек либо ищет ответ по сайту вручную, либо пишет письмо «в никуда» и ждёт.
Для поступающего это особенно болезненно: сроки подачи документов жёсткие, а сайт большой.
Поддержка в ответ получает обращения без половины нужных данных и тратит время на переписку
ради уточнений.

Помощник снимает обе боли сразу: типовые вопросы закрываются ссылкой на существующий раздел
и не доходят до людей, а то, что доходит, приходит уже структурированным, с подтверждённым
автором и без круга уточнений.

### Поток

```
главный экран: ползунок «поступающий / студент / преподаватель» + «Задать вопрос»
   │
   ├── РАЗДЕЛ «ЗАДАТЬ ВОПРОС» — привычный чат языковой модели
   │      ├─[код]   роль уже известна → берём индекс FAQ только её аудитории
   │      ├─[LLM]   разбор вопроса: суть, сколько вопросов задано, ключевые понятия
   │      ├─[алг]   поиск по индексу ключевых слов (в промпте только они, без содержания)
   │      ├─[инстр] get_article(id) — подгружает текст только выбранных разделов
   │      ├─[инстр] fetch_page(url) — если в базе нет, читает раздел misis.ru
   │      ├─ нашли ──→ выжимка по вопросу + ссылка на первоисточник
   │      └─ не нашли ─→ «Ответа у меня нет. Создать обращение?»
   │
   └── РАЗДЕЛ «СОЗДАТЬ ОБРАЩЕНИЕ»
          ├─ развилка: подтвердить почту кодом ИЛИ остаться инкогнито
          ├─[код]   проверка полноты по реестру полей роли и категории
          ├─[LLM]   уточняющие вопросы строго по недостающим полям
          ├─[LLM]   сборка текста обращения и темы письма
          └─[код]   письмо в поддержку; ответ приходит только авторизованным
```

### Почему поиск двухступенчатый

В промпт кладутся **только ключевые слова и заголовки** разделов нужной аудитории — не их
содержание. Модель выбирает, что именно открыть, и содержание подгружается инструментом по
идентификатору. Если раздела нет и в базе — инструмент читает страницу misis.ru напрямую.

Это даёт три вещи разом: запрос не раздувается и остаётся в лимитах, база знаний растёт без
переписывания промпта, а сам переход «выбрал раздел → открыл его → ответил» и есть агентная
часть проекта, которую требует кейс.

### Экраны

1. **Главный** — ползунок роли (поступающий / студент / преподаватель) и кнопка «Задать вопрос».
2. **Чат помощника** — привычный интерфейс языковой модели, без лишних настроек. Два раздела:
   «Задать вопрос» и «Создать обращение».
3. **Предложение обращения** — появляется прямо в чате, когда ответа в базе нет.
4. **Развилка доступа** — «подтвердить почту» или «остаться инкогнито» с честным
   предупреждением: без подтверждения ответ прийти не сможет.
5. **Подтверждение почты** — адрес, затем код из письма.
6. **Уточнение** — помощник спрашивает только то, чего не хватает.
7. **Обращение отправлено** — номер, тема письма, что будет дальше.

### Профиль и расписание

После подтверждения почты человек один раз рассказывает о себе: студент — институт и группу,
преподаватель — кафедру и фамилию. Поступающему заполнять нечего. Данные сохраняются за
почтой, при следующем входе не спрашиваются.

Это открывает быстрые кнопки: **«Расписание на сегодня»**, «на завтра», «на выбранный день».
Помощник уже знает группу и отвечает списком пар — время, предмет, тип занятия,
преподаватель, аудитория.

**Расписание разбирается без языковой модели.** Это таблица, а не текст: чистый алгоритм
читает `.xls` по институтам и отдаёт нужный день. Модель здесь только добавила бы задержку,
стоимость и шанс выдумать несуществующую пару. Формат файлов разобран в
[team/nyonless/task/format-raspisaniya.md](team/nyonless/task/format-raspisaniya.md).

Это же — лучший ответ на вопрос жюри «где вы применяете модель, а где обычную логику»:
у нас есть живой пример задачи, от которой модель осознанно отключена.

### Хранение данных

Все данные лежат в одном томе: база знаний, файлы расписаний, SQLite с профилями и
обращениями, кэш ответов модели, исходящие письма. Приложение обращается к нему через
`DATA_DIR` и не знает, запущено оно локально или в контейнере.

## Куда что класть

Папки созданы заранее, в каждой лежит `README.md` с правилами. Ничего не создавайте рядом —
пути зашиты в коде и в постановках.

```
team/<кто>/          папка участника: маршрутный лист, постановка, свои материалы
app/                 серверный код (Python)
web/                 интерфейс: index.html, style.css, app.js
tests/               тесты
data/faq/            база знаний по ролям
data/schedule/       .xls расписаний по институтам
docs/                контракты, разбор кейса, донорский проект
```

Начинать всем с [`team/<кто>/README.md`](team/) — там маршрутный лист: что делаешь,
что прочитать, куда класть результат. Постановка лежит там же.

Код и данные, которые читает приложение, остаются на общих путях — иначе оно не запустится.
Всё некодовое — в своей папке, в `materials/`.

## Работа в команде

**Ветки**

- `main` — защищённая, только через PR. Всегда должна собираться.
- Рабочие ветки: `feat/<area>-<кратко>`, `fix/<area>-<кратко>`, например `feat/core-llm-client`.
- Одна задача = одна ветка = один PR. Ветку берём от свежего `main`.

**Правила, чтобы не ловить конфликты**

- За каждым участником закреплена своя зона (каталог/модуль). В чужую зону — только через договорённость.
- Контракты (схемы запросов/ответов, интерфейсы модулей) фиксируются ДО реализации и меняются отдельным PR с уведомлением команды.
- `git pull --rebase origin main` перед пушем.

**PR**

- Название: `[area] что сделано`.
- В описании: что делает, как проверить, какие переменные окружения нужны.
- Мержим только зелёный PR; ревью — минимум один человек.

**Задачи**

Постановка лежит в папке своего исполнителя: `team/<кто>/task/` — самодостаточное ТЗ, которое можно целиком скопировать в чат с LLM и получить рабочий код. Каждой постановке соответствует задача на GitHub, там же указано, в какую папку класть результат.
