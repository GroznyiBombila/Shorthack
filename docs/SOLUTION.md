# Решение: «Диспетчер первой линии»

Сценарий: сотрудник поддержки получает сырое обращение (письмо или расшифровку звонка) и
за один шаг получает готовую карточку заявки, решение о следующем действии и готовый текст
для отправки клиенту.

**Пользователь решения** — оператор первой линии техподдержки университета/компании.
**Что становится проще** — исчезает ручной разбор: суть, категория, приоритет, команда,
чего не хватает и что написать клиенту приходят уже готовыми.

## Ключевая идея

Обращение редко бывает одним вопросом. Помощник **раскладывает одно письмо на несколько
самостоятельных заявок**, по каждой отдельно проверяет полноту данных и выбирает действие.
Это прямо закрывает два пункта входа из ТЗ — «неполная информация» и «несколько вопросов
в одном сообщении» — которые обычно игнорируют.

## Пайплайн

```
сырой текст
  │
  ├─[код]  нормализация, определение типа (письмо / расшифровка), маскирование ПДн
  │
  ├─[LLM]  ИЗВЛЕЧЕНИЕ (один вызов, строгий JSON):
  │         • декомпозиция на N самостоятельных обращений
  │         • по каждому: суть, категория (фикс. enum), извлечённые поля,
  │           тон клиента, маркеры срочности, цитаты-обоснования
  │
  ├─[код]  ПРОВЕРКА ПОЛНОТЫ: реестр обязательных полей по категории → чего не хватает
  ├─[код]  ПРИОРИТЕТ: детерминированные правила (P1..P4)
  ├─[код]  МАРШРУТ: таблица «категория → команда»
  ├─[алг]  ПОХОЖИЕ ЗАЯВКИ: эмбеддинги + косинус; N похожих за окно → массовый инцидент
  │
  ├─[код]  ВЫБОР ДЕЙСТВИЯ (детерминированный роутер):
  │         данных не хватает      → request_clarification
  │         данных хватает         → create_ticket + draft_reply
  │         похоже на инцидент     → attach_to_incident
  │
  ├─[LLM]  ГЕНЕРАЦИЯ ТЕКСТА: уточняющие вопросы (только по недостающим полям)
  │         или черновик ответа по базе знаний
  │
  └─ карточка заявки + выполненное действие + лог «почему так решили»
```

## Где LLM, а где обычный код

Это отдельный пункт защиты, поэтому граница проведена жёстко.

| LLM отвечает за | Код отвечает за |
|---|---|
| Понимание естественного языка: суть, декомпозиция на под-обращения | Достаточно ли данных для заявки |
| Извлечение сущностей (сервис, устройство, ОС, логин, время, код ошибки) | Приоритет P1–P4 |
| Классификация категории из фиксированного списка | Маршрут в команду |
| Оценка тона и маркеров срочности | Какое действие выполнить |
| Генерация текста уточнения и черновика ответа | Дедупликация и детект массового инцидента |
| Эмбеддинги для поиска похожих | Валидация JSON, ретраи, хранение, аудит решений |

**Тезис для жюри:** LLM не принимает решений — она только превращает текст в структуру и
структуру обратно в текст. Все решения принимает детерминированный код, поэтому они
воспроизводимы, объяснимы и проверяемы тестами.

## Модель данных заявки

```
Ticket:
  id, created_at
  source_type        письмо | расшифровка звонка
  raw_text           исходник целиком
  title              одна строка
  summary            2-3 предложения для оператора
  category           account | edu_platform | wifi_network | hardware | software | other
  priority           P1..P4  + priority_reason (какое правило сработало)
  assigned_team      из таблицы маршрутизации
  extracted_fields   {поле: значение} — что LLM нашла в тексте
  missing_fields     [поле] — чего не хватает по реестру категории
  status             new | awaiting_info | routed | merged_into_incident
  parent_request_id  если это одно из N обращений в письме
  similar_ticket_ids найденные похожие
  action             create_ticket | request_clarification | draft_reply | attach_to_incident
  action_payload     сгенерированный текст
  trace              лог: что решила LLM, что решил код, по какому правилу
```

`trace` — не украшательство: это то, что показывается на защите в ответ на вопрос
«как результат LLM влияет на действия программы».

## Категории и обязательные поля (детерминированный реестр)

| Категория | Обязательные поля |
|---|---|
| `account` | логин/почта, ФИО, что именно не работает, текст ошибки, когда началось |
| `edu_platform` | название платформы, курс/предмет, роль (студент/преподаватель), шаги воспроизведения |
| `wifi_network` | корпус/аудитория, устройство и ОС, когда началось, у других та же проблема? |
| `hardware` | модель/инвентарный номер, местоположение, характер неисправности |
| `software` | название и версия ПО, ОС, текст ошибки |
| `other` | описание, контакт для связи |

## Правила приоритета (код, не LLM)

- **P1** — массовый инцидент (≥3 похожих за 30 мин) ИЛИ полная недоступность сервиса ИЛИ упомянут жёсткий срок (экзамен, сессия, сдача).
- **P2** — пользователь полностью заблокирован в работе, обходного пути нет.
- **P3** — работает частично или есть обходной путь.
- **P4** — вопрос, консультация, пожелание.

## Объём работ по этапам

| Этап | Что готово | Срок |
|---|---|---|
| MVP (обязательный минимум ТЗ) | текст → LLM-извлечение → карточка → создание заявки в БД, видно в UI | T+2:00 |
| Полнота данных | реестр полей, `missing_fields`, генерация уточняющих вопросов | T+3:00 |
| Решения | приоритет, маршрутизация, `trace` | T+3:30 |
| Похожие заявки | эмбеддинги, косинус, детект массового инцидента | T+4:15 |
| Черновик ответа | генерация по мини-базе знаний | T+4:45 |
| Заморозка | стабилизация, прогон демо, слайды | T+5:00 |

Всё, что не успевает к T+5:00, вырезается без сожаления. Обязательный минимум ТЗ
закрывается уже на этапе MVP — дальше только наращивание ценности.

## Риски

| Риск | Что делаем |
|---|---|
| Модель возвращает невалидный JSON | Строгая схема + один ретрай с указанием ошибки + фолбэк на «одно обращение, категория other» |
| Лимиты/недоступность API организаторов | Кэш ответов на диск по хэшу входа: демо работает даже без сети |
| Промпт-инъекция из письма клиента | Вход трактуется как ДАННЫЕ (блок правил портирован из донора), действия выбирает код, а не текст модели |
| Не успеваем к дедлайну | Порядок этапов такой, что демо есть уже с T+2:00 |
| Демо падает на защите | Заранее записанный скринкаст + 3 проверенных обращения-эталона |

## Распределение

| Кто | Зона | Что отдаёт |
|---|---|---|
| alexa + Sonnet | ядро | YC-клиент, промпты, схема извлечения, пайплайн, роутер действий, API |
| nyonless | детерминированный слой | реестр полей, правила приоритета, таблица маршрутизации, валидация — чистые функции + тесты, без зависимости от LLM |
| antitaxi | интерфейс и защита | страница «обращение → карточка → действие», слайды |
| Стася | данные и демо | 25 обращений (письма и расшифровки: неполные, многовопросные, эмоциональные), мини-база знаний по 5 категориям, прогон сценария |

Зона nyonless не зависит от ядра: контракт — чистые функции над готовым dict.
Зона Стаси отстёгивается: если участника нет, датасет генерируется за 10 минут.
